Multi-Agent Workbench 架构评审

Opus 5 只做拆解与审查，重活下放 GLM-5.3 / DeepSeek V4-Pro。下面 5 张图与《实施计划》一一对应——你逐图 check，通过即定稿（Revision 2）。

00设计不变量

看图前先认这 5 条——所有图都由它们推导出来，任何一条不认，架构就要重画。

  1. 单 gateway 进程——WS Hub / 编排 / 执行器管理 / 信箱同进程，MVP 不做分布式。
  2. 单写者 DB——所有写经主线程写队列，任意时刻至多 1 个写者。
  3. 事件溯源——一切输出先落 events 表（单调 seq），WS 只是广播层；恢复靠重放。
  4. ExecutorAdapter 是唯一扩展点——加 OpenCode / Aider / PTY 只加 adapter，不碰总线与 UI。
  5. AG-UI 只当词汇表——TS 类型本地持有，不硬依赖其 pre-1.0 运行时。

B端到端任务生命周期

审查循环是任务状态的唯一出口；人只在审批队列、页签干预、最终合并三处介入，绝不当搬运工。

sequenceDiagram
    autonumber
    actor H as 人类
    participant UI as Web
    participant Hu as WS Hub
    participant M as Master / Opus 5
    participant R as Router
    participant W as Worker / GLM-5.3 或 DSV4
    participant DB as SQLite
    H->>UI: 提交自然语言目标
    UI->>M: POST /api/tasks
    M->>M: 拆解为任务树 JSON
    M->>R: 复核 model_hint
    R-->>M: 档位决策 glm53 / dsv4 / claude
    M->>DB: tasks 入库 status=queued
    loop 按依赖拓扑 dispatch
        M->>W: spawn (worktree + spec)
        W-->>Hu: 流式事件 (events 表 seq++)
        Hu-->>UI: 实时推送 (agentId 路由到页签)
        W->>DB: report 信箱消息
        M->>DB: 消费 report
        M->>M: Opus 审查 diff
        alt 审查通过
            M->>DB: status=done · 解锁下游
        else 审查不过 且 attempts 少于 2
            M->>W: re-dispatch + feedback
        else 2 轮失败
            M->>DB: status=awaiting_approval
            Hu-->>UI: 推入审批队列
            H->>UI: 人工裁决
        end
    end
    M-->>UI: 汇总 diff · 人工 review 后合并

E崩溃恢复

kill -9 后重启：存活的 executor 直接 reattach，死了的回队重拉，事件从 sinceSeq+1 重放。

F关键决策记录

这 6 条是架构的“合同条款”——评审时重点确认，任何一条不同意都请在回复里点编号。

#决策理由不同意的后果
1WS 单通道 + AG-UI 词汇表避免自发明协议；类型本地持有防绑定换协议需重写前端事件层
2单写者 SQLite（WAL）14 天内可交付的崩溃恢复最简路径上量后迁 Postgres + pgmq（接口已预留）
3Claude 走 Agent SDK；GLM/DSV4 走 ai@6各自控制面五要素零成本Agent SDK 不可用时降级 headless CLI stream-json
4MVP 不引入 CCR只有 2 条接入路径，自研 gateway 更透明多 CLI 混编时再加 CCR adapter
5仅 API-key 计费Anthropic ToS 禁订阅 OAuth（2026-02 起）违规封号，不可逆
6信箱模式 agent 间通信抄 Claude Code mailbox 已验证结构引入独立 MQ 则 MVP 复杂度超标

第 5 条是不可逆红线：任何“拿订阅账号做 worker”的捷径都不在方案内。
